# Content audit · 25 October 2026

ENG-325. Audited the live catalog on `main` at `fbca649` (PR #32): 46 issues in 7 projects. This audits and revises existing issues; it adds none. The JavaScript and Python paths are covered in full. Other languages are covered only where they share a file or a rule with them, and their remaining weak points are listed at the end. This does not validate the whole catalog.

## What was checked

For every JavaScript and Python issue, and the TypeScript multi-file ones:

1. **The ticket stands on its own.** It gives realistic symptoms (a support ticket, a log, a receipt, an import log), the stakes, and every requirement the cases check. The title and summary name the symptom, not the cause or the fix. There are no incident prerequisites (paging, on-call, tools being down) and no file named after the answer.
2. **Clues are read-only and useful.** The ticket's thread holds what a teammate would know. Later comments are actionable findings (blocking or nit) or hints released by behaviour. Ambient lines (praise, "I'll tell support", chat) were removed.
3. **Every file a reasonable fix touches is editable.** No read-only file has to change for a correct fix.
4. **Checks test behaviour.** Cases decide merging. A review comment that blocks may only enforce a requirement the ticket states, and may not fire on any correct design.
5. **Fairness is shown, not asserted.** Each issue names correct alternatives, which must pass every case and fire no blocking comment, and plausible wrong fixes, which must each fail a case. `npm run check:publish` runs all of them in the browser sandbox.
6. **PR feedback needs explicit Resolve.** Every blocking and nit review comment carries `resolve: "explicit"`. Informational notes never do (asserted in `incident.test.ts`).

Rules 4 to 6 are now enforced by the content build (`packages/content/publish.ts`, tests in `publish.test.ts`):

- a blocking comment may not fire on any alternative;
- a JavaScript or Python issue needs at least one alternative and two wrong fixes;
- `continuityProblems`: a new live revision may add editable files, but never remove, rename or lock one, and never rename the entry point.

## Contracts for the other streams

**Issue identity.** Ids, keys and project placement are unchanged: an issue's key is its project's key plus its position, and later issues only append. INC-1 keeps its id (`checkout-guest-shipping`), its project id (`incident-response`) and its key `INC`, because recorded work names both `issueKey: "INC-1"` and the id. Its project is now an ordinary listed project titled "Checkout".

**Versions.** A revision is the SHA-256 of its content. Every earlier revision stays in `content/catalog.json`, including INC-1's played incident revision `sha256:ea2bec9e…` with its chat. The catalog was rebuilt once from the baseline, so no unplayed intermediate revision was added. Only `--prune` drops old revisions, and it must not be run while records name them.

**Required files.** Saved code is restored onto the live revision by path (`latestSavedCode` → `files[path] ?? starter`). The build refuses a revision that would drop an editable path or change the entry point, so a content update cannot strand an active attempt's code. Making a file editable is safe: it opens with its starter text. Note that `docs/issue-model.md` still says "work in progress on an older one keeps its own", but the IDE opens the live revision unless `?revision=` is given. That routing belongs to ENG-322 and ENG-326.

## Remaining weak cases

These are known and not fixed here:

- **Requirements the cases can't see.** "Keep it one pass" (FN-4, DATA-7), "keep the memo" (SHOP-7), "the label printer gets inches too" (FN-3), "checkout totals are out of scope" (SHOP-5), "input rows are not changed" (DATA-7) and "`raw_settlements` keeps the partner's sign" (DATA-8) are enforced only by text-pattern review comments, so renaming can dodge them. Explicit Resolve lets a person with a valid design clear them. A runner would need scaling checks (not built) or a second entry point to test them.
- **Patterns, not syntax.** Every code-reading trigger is a regular expression (`print(`, `catch`, `25.4`, `abs(`), as `docs/issue-model.md` says.
- **Other languages are unaudited for fairness.** TypeScript (SHOP-2, SHOP-4, SHOP-8, API-3, API-9), Go, Java, C#, Ruby, PHP, C, C++, SQL and HTML issues have a reference only, with no alternatives or wrong fixes. SHOP-8 still blocks `toFixed`/`parseFloat` anywhere, and several single-file tickets (DATA-3/4, EDGE-1/3/4) still read as specs more than reports.
- **One fixed reading per issue.** Hidden cases still pin choices a ticket now states. A reader who skips the ticket can still be surprised by them.
- **Automated runs are QA, not validation.** Alternatives and wrong fixes show that the checks discriminate. They are not evidence that people find the issues fair or realistic.
