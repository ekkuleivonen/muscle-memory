# ENG-376: current comparison privacy — approval proposal and draft

This is an unconfigured draft, based on merged PR71 (`ca9556b`). Human cohort reads remain disabled. Neither the new public privacy write nor internal member-check RPC is enabled in live configuration. No credentials, new service, database, model runs, collection events or runtime editor features are added. ENG-375 output-first results and the managed private catalog are preserved.

## Exact proposed authority

- Browser → existing **muscle-memory-ingest**: `POST /ingest/v1/participants/<id>/comparison-privacy`, JSON `{ secret, expectedRevision, stealth, age }`. `age` is exactly `adult`, `non-adult`, or `unknown`, derived from the existing optional age answer; unknown is never adult. Original device secret is checked against the current CONTROL ownership proof, never the cached upload proof. Existing participant/address rate-limit bindings apply. Absent proof, wrong secret, or deletion refuse the write. No first-claim operation is added. Requires `COMPARISON_PRIVACY_ENABLED="true"` on ingest; variable deliberately absent today.
- Stored in existing **CONTROL**, only at `comparison-privacy/<validated-browser-id>`: `{ stealth: boolean, age, revision: <random server UUID> }`. No birth date, full profile, raw event, code, secret, proof or client timestamp. UUID is a concurrency token, not a sortable timestamp. Conditional R2 ETag writes prevent concurrent/stale updates from overwriting a successful change. `expectedRevision=null` is create-only; an authenticated 409 may return the current revision for explicit settings review, never an automatic retry of a permissive stale preference. Uploads do not write these keys. This is persistent control state, requiring explicit approval/disclosure. Deletion tombstones override it even if a write races with deletion; existing erasure timelines stay unchanged. A later retention cleanup should remove the redundant privacy object after deletion without removing its tombstone.
- Existing **muscle-memory** web Worker → existing **muscle-memory-ingest**, new named entrypoint **ComparisonEligibility**, proposed binding **COMPARISON_ELIGIBILITY**. Only callable domain method: `check(members: string[])`, at most **100 unique validated browser IDs**, returning an aligned array of eligible state revisions or null. It checks CONTROL privacy and tombstones without caching. No secret needed on this trusted service boundary. It cannot access arbitrary keys, SQL, records, ownership proofs or device secrets through its API. Storage errors become a fixed error. This entrypoint is separate from **ParticipantOwner**, whose approved `verify(participant, secret)` authority is unchanged. Browser HTTP cannot call `check`.
- Web retains existing **ADMIN_STATS_SQL_TOKEN**, unmodified. The query is fixed to a registered current challenge/revision, never caller SQL, IDs or demographic filters. SQL now returns member IDs internally so current eligibility can be enforced. They are discarded before the aggregate response. Public output remains `CohortRead` only. The server does two uncached member checks; changed revisions, failures or malformed replies reject the read. No aggregate/member cache or stale fallback.

## Exact configuration changes proposed — none made

After explicit approval forwarded by dot, install ingest variable `COMPARISON_PRIVACY_ENABLED="true"`; add web service binding `{ "binding": "COMPARISON_ELIGIBILITY", "service": "muscle-memory-ingest", "entrypoint": "ComparisonEligibility" }`. No additional R2 binding on web, token copy or token permission change. Both named entrypoint code and HTTP dispatch are fail-closed unless the ingest variable is true. Browser transport has a separate source constant `COMPARISON_PRIVACY_ENABLED=false`. `COHORTS_ENABLED=false` remains independent. Approving control authority would not approve either cohort enablement or release. Privacy Notice wording/version and final merge/deploy require separate review/instruction.

## Publication guarantee is still a release blocker

Two passes detect a privacy/deletion change observed during member checking. They do **not** provide atomicity between the last CONTROL read and HTTP publication: a privacy change can be acknowledged in that interval. An R2 epoch does not fix that race either; its own check has the same interval. Per-isolate locking is not cross-isolate coordination. This draft intentionally does **not** claim the requested strict acknowledgement guarantee is implemented and must not be activated on the strength of these checks alone.

Before activation, agree the publication linearization boundary with dot and prove it against concurrent writes/deletion, or refine the existing-service protocol to fence publication. No new coordination service or global lock platform is authorized. Already downloaded aggregates cannot be retracted; that is distinct from allowing a fresh read to count an excluded browser. No aggregate cache is present to obscure this distinction.

## Browser behavior and unfinished integration

Local stealth/age changes continue to take effect immediately. The draft transport maps existing age bands, uses the original device secret with a deadline, reports pending/confirmed/conflict, sends nothing while disabled, and never retries a conflict automatically. It is **not yet wired into settings**: a complete controller must scope acknowledgements to browser identity plus the exact current preference, discard obsolete responses across edits/import/delete/reset, show pending/offline versus confirmed exclusion, and require review for stale-tab re-enablement. Reload/conflict recovery must be designed before enabling. Do not call a local setting a server confirmation. Stealth still does not stop recording/uploads; retention and erasure promises remain unchanged.

Suggested disclosure: “Stealth hides your report on this device immediately. Exclusion from future comparisons is confirmed when the server accepts the change. While offline or pending, server exclusion is not yet confirmed. Previously downloaded aggregate results cannot be recalled.” Adult-only comparisons are unavailable to minors and unanswered ages; optional profile completion is never required for private statistics.

## Bounds and remaining evidence

The draft caps SQL response streaming at 1 MiB with a 15-second fetch deadline, row output at 1,000 (1,001 is overflow sentinel), and unique member checks at 100. Each pass costs at most 300 CONTROL reads, so two passes cost at most 600, plus SQL/catalog calls. Runtime conditions and first/repeat stay separate; the 20-browser floor applies separately to first-try and finisher metrics. Rates are rounded but boundary changes can still reveal membership: threshold/rounding do not guarantee anonymity. Duplicate browser units and invalid numeric aggregate values reject rather than inflate counts.

Web permits two concurrent queries and one query per revision per minute **per isolate**, with at most 128 recent keys. These are not a global spending cap. No cache coalescing silently extends privacy freshness. The SQL still needs an explicit bounded server-time window and treatment of first/repeat at window edges before activation; existing whole-revision scanning is not represented as a bounded date range. Complete editor/tool compatibility (beyond the existing runtime/diagnostics dimensions), capture completeness and per-metric denominator audits also remain activation gates.

Synthetic Node tests cover original-secret authorization, disabled/arbitrary methods/paths, conditional concurrent writes, stale revisions, missing/unknown/non-adult/stealth state, deletion before/during lookup, control failure, invalid IDs, duplicates/limits, 20→19 suppression, changes between checks and fresh subsequent reads. Existing SQLite tests cover newer conflicting profiles, delayed profile ordering, duplicate deliveries, first/repeat and revisions. The DataFusion test uses JSON stand-ins and is not native Basin verification.
