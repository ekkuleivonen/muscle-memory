# Practice

`/challenges/<KEY>` (for example `/challenges/PY-002`, always on the challenge's live revision) is where a challenge is worked: the challenge on the left, the code over its feedback on the right, as terminal panes (`apps/web/app/practice/practice.tsx`).

## The loop

- **Run examples** (⌘↵ or Ctrl+Enter, including from the editor) runs the examples (the visible cases) against the code and changes nothing else; run as often as you like. Its feedback shows every example: input, expected value and what came back, with errors and printed output. A short result is announced to screen readers. Run and Submit keep keyboard focus during checks and become Cancel check while their own check is running.
- **Submit** is available only after public examples pass for the exact current code and runner. Any edit (including paste or undo), new session/challenge/language, runtime replacement/failure or a new example run invalidates that prerequisite; a stale/late result cannot restore it. Both the button and actual session handler enforce it. Model tool runs retain their separately versioned protocol. Submit runs every case, the hidden ones included, then reads the verdict (`apps/web/lib/submission.ts`): whether every case passed and which rules the code fires. Hidden failures are grouped by safe failure category, with their individual positions and categories available in a closed Details list; and a submission with hidden cases shows neither printed output nor a run-level error's text, since user code can read the inputs while it runs (`apps/web/lib/diagnosis.ts`, `apps/web/lib/check-feedback.ts`).
- **Complete** when every case passed and no rule fires. The attempt is completed (recorded as `practice.completed`, kept in `muscle-memory.progress`), and the feedback leads with the verdict and expanded Output. Next challenge sits beside Submit as a separate action; submitting again never navigates. The next suggestion (`apps/web/lib/next-problem.ts`) runs here, in the same language, then a profile language, at about the same difficulty. After output, Share opens its existing consent-preserving dialog directly. A quiet one-line code-length FYI and occasional optional reflection can appear ([start and sharing](start.md)).
- **Attempts.** Opening a challenge resumes its attempt where it was left, completed or not; a start after a completed attempt (from the list, quick start, a link, the next suggestion) begins a new one. What is recorded is in [telemetry](telemetry.md).
- The challenge's title row has a star (☆/★), as in the list.

## Layout and keys

Each pane is bordered, titled in its top border and scrolls on its own; the pane holding focus is outlined in the accent colour. Panes are numbered `[1] challenge`, `[2] code`, `[3] feedback`, as in lazygit: while focus is within the practice panes, outside the editor, other text fields and dialogs, 1, 2 or 3 moves to that pane (Escape then Tab leaves the editor first). There is deliberately no chord from inside the editor, since AltGr and Ctrl with digits type characters or switch browser tabs. The lines between the panes can be dragged (arrow keys nudge a focused one, Shift moves faster, Home/End reach the limits, and Enter or double-click resets; screen readers hear the current size in pixels); the sizes are kept on this device under `muscle-memory.practice-layout` and never recorded. Under the panes are a status line (shortcuts, editor keys; left out on touch screens, where keys don't apply) and the site's status bar. Below 760px, and on phones held sideways, the panes stack and the page scrolls; sticky Challenge, Code and Feedback buttons move focus and restore each pane’s reading position without unmounting the editor. Practice is desktop-first: on a phone (a touch screen under 600px wide or 500px tall) a challenge link still opens that challenge to read, under “Open on a computer to solve.” with its link to copy or share, and **Solve here anyway** shows the panes for the rest of the tab (`muscle-memory.solve-here` in session storage, best effort: where storage is blocked the choice still holds on that page; never recorded). The editor is mounted throughout, so code and progress carry on either way. Tablets and narrow desktop windows keep the workspace; a phone with a keyboard attached can solve here anyway. The list’s challenge titles wrap instead of truncating. Opening practice focuses the editor without scrolling to it, so the challenge stays in view. Escape deliberately collapses an editor selection; use CodeMirror’s Tab-focus-mode toggle (Option+Shift+M on macOS, Ctrl+M elsewhere), then Tab, when leaving with a selection intact.

## Runtime isolation

Submitted code never runs in the app's JavaScript context, in Node or on a server. A case's input and expected output follow the [challenge model](challenges.md).

- **Sandbox.** Each run gets a new `sandbox="allow-scripts"` srcdoc iframe. That gives an opaque origin with no access to the app's DOM, cookies, localStorage or IndexedDB. Inside it, a classic dedicated worker runs the challenge's language. Every language uses this same boundary and message protocol; an engine (`packages/runner/engines.ts`) only adds its worker source (`packages/runner/workers/`) and pinned files:
  - **Python**: Pyodide, as below.
  - **JavaScript and TypeScript**: the browser's own engine. Sucrase strips TypeScript types, keeping line numbers, and every source file becomes an ES module at a blob URL, its relative imports (`./discounts`, `../money.js`) rewritten to its siblings' URLs; package imports are not available. A missing or circular import is a compile error naming the files, and a stack trace points at the file and line it came from. Nothing is type-checked when running. Each case gets a fresh copy of its input; a returned promise is awaited; values JSON cannot hold (NaN, BigInt, undefined) are refused rather than guessed.
  - **SQL**: PGlite, which is Postgres 18 compiled to WebAssembly. Each case runs in its own transaction, rolled back afterwards: the schema is created, the case's rows inserted, then the solution's statements run. Errors read like psql's, with the line and a caret.
  - **HTML**: checked the way frontend tests check a page. The markup is parsed into a DOM with linkedom (no scripts run, nothing loads) and each case is `[selector, read]`: the number of matches (`count`), their `text`, each form control's accessible `label` (aria-labelledby, aria-label, then its label), or an attribute.
  - **PHP**: php-wasm (PHP 8.4, used under its Apache-2.0 licence option). The solution is written into PHP's in-memory file system at its path and required, so errors name the right file and line; echo and warnings are its output. Its sockets are emulated over WebSocket, which the sandbox refuses, so none ever connects.
  - **Ruby**: ruby.wasm (CRuby 3.4 with its standard library). Inputs go in as Ruby literals and results come back through a small JSON encoder; `puts` is its output.
  - **Go**: Yaegi, the Go interpreter, with Go 1.25's standard library, built to WebAssembly from `tools/runtimes/go` (our own harness, not a prebuilt binary). The harness evaluates the solution's package and calls the entry point per case, decoding each JSON input into the function's real parameter types with reflection. A two-value return follows Go's idioms: a false `ok` or a non-nil `error` is reported as `null`. Runs happen on a goroutine, so code that blocks (channels, `time.Sleep`, `net/http`) works; `net/http` goes through fetch, which the sandbox refuses. Panics stay with their case, with the line Yaegi reports.
  - **C and C++**: Clang/LLD 22 compiled to WebAssembly (YoWASP), targeting WASI with wasi-libc and libc++. C has no reflection, so a C or C++ challenge carries an `adapter`: a few lines that turn a case's JSON arguments into the function's types and the result back, using a small JSON library (`mm_json.h`) the runner compiles in. The program (solution, adapter, library and a `main` that reads the case from stdin) is compiled once per run, at `-O1` for C and `-O0` for C++, then each case runs as a fresh instance with only WASI imports, so a crash stays with its case. Because the program never runs in the worker's JavaScript, this sandbox is kept between clean runs: loading LLVM takes seconds, a rerun about half a second. Runs may take up to 30 seconds, compile included. On some hosts the browser's renderer dies on any WebAssembly memory trap (out-of-bounds access, C stack overflow) instead of throwing a catchable error; the browser check probes for that and reports the crash case as skipped there.
  - **C#**: .NET 9 compiled to WebAssembly with Roslyn 4.12 (C# 13), built from `tools/runtimes/csharp` in a digest-pinned .NET SDK image. Roslyn compiles the solution in memory against a curated set of the framework's reference assemblies (System.Runtime, collections, LINQ, regular expressions, numerics, System.Text.Json and a few more; no networking or file system), with `System`, `System.Collections.Generic` and `System.Linq` imported. The entry point is the public static method of that name; each JSON input is decoded into its parameter's type with System.Text.Json, and the result is encoded with camelCase names. Exceptions name the methods they went through, but not lines: writing the debug information that would map them needs a second thread. The runner's `Main` is called once per run with the request in .NET's in-memory file system, rather than through `[JSExport]`, whose generated wrappers get random names and would make builds differ.
  - **Java**: teavm-javac, which is OpenJDK 25's javac and the TeaVM compiler, both compiled to WebAssembly (WasmGC, so it needs a current Chrome, Edge or Firefox), built from a pinned commit in a digest-pinned JDK image. javac compiles the solution, the challenge's adapter and a small JSON library (`Json`); TeaVM turns the classes into a WebAssembly program, and each case runs as a fresh instance of it with the case's arguments as `main`'s only argument. As with C and C++, a Java challenge carries an `adapter`, because TeaVM keeps almost no reflection. TeaVM's class library covers most of `java.lang` and `java.util` (collections, regular expressions, `String.format`), not files or networking. Its own JavaScript interop (`org.teavm.jso`, `@JSBody`) is refused as a compile error. Exceptions show their type and message; without debug information TeaVM has no useful stack frames. A run takes one to three seconds, javac and TeaVM included.
  - **One exception to the sandbox's policy**: TeaVM's loader builds its JavaScript glue from source text, so the Java engine's frame allows `eval` (`allowEval` in `engines.ts`). It gives code nothing new: the frame is still an opaque origin with every connection, storage and the parent denied, and the JavaScript engine already runs arbitrary user code in the same kind of frame. Every other engine's frame refuses `eval`.
- **No network.** The frame's CSP is `default-src 'none'; connect-src 'none'; script-src '<boot-hash>' blob: 'wasm-unsafe-eval'; worker-src blob:`, plus `'none'` for every other fetch directive. Blob workers inherit it. There is no `unsafe-eval`.
- **Runtime files, sent once.** Each sandbox gets its own copy of the runtime's bytes, transferred rather than copied into the frame and on to its worker (runtimes run to 100 MB); the page keeps none and reloads from the HTTP cache, re-checking the hashes.
- **Runtime files.** Pyodide `314.0.7` (Python 3.14.2, about 13 MB), Sucrase `3.35.1` (one 47 KB bundle, gzipped), PGlite `0.5.11` (Postgres 18.6, about 5.5 MB gzipped), linkedom `0.18.14` (110 KB gzipped), php-wasm `0.2.0` (PHP 8.4.1, about 3.5 MB gzipped) ruby.wasm `2.10.1` (Ruby 3.4.1, about 9 MB gzipped) Yaegi `0.16.1` (Go 1.25.3, about 8 MB gzipped) YoWASP Clang `22.0.0-git20542-10` (about 27 MB gzipped), the C# runner (Roslyn `4.12.0` on .NET 9, about 8 MB gzipped) and teavm-javac `208d4c9` (about 4.5 MB gzipped) are pinned in `package-lock.json` and `packages/runner/runtime-manifest.json`. The `predev`/`prebuild` step `tools/build-runtimes.mjs` copies the binaries from `node_modules`, bundles the JavaScript pieces into single files with esbuild, writes them into the app's static assets and verifies every SHA-256 hash; after upgrading a package, `node tools/build-runtimes.mjs --update` rewrites the pins. The Go, C# and Java runners are built from source in images pinned by digest (Docker is required for the build); identical inputs give identical bytes, and builds are cached in `node_modules/.cache` by their inputs. Files over Cloudflare's 25 MiB static-file limit ship gzipped (`.gz`); the page checks the compressed bytes' hash, then unpacks them before handing them to the sandbox. The sizes are pinned too, so practice's opening screen can show download progress. A page loads only the engine its challenge needs. Nothing loads from a CDN.
- **Loading inside the sandbox.** Only the trusted app page fetches the files. It uses its own origin only (`mode: "same-origin"`; an asset base on another origin is refused) and the site's existing sign-in, such as the Cloudflare Access cookie on the owner preview (`credentials: "same-origin"`). Subresource Integrity checks every file. Any redirect, for example to a sign-in page after the session expires, fails closed instead of being followed. The page then posts the bytes into the frame; the sandbox never sees credentials and makes no requests. The worker answers Pyodide's file reads from memory. Only the standard library is available: the package lock is empty, so other imports fail without any request.
- **Timeout and cancel.** A finished, timed-out (5 s) or cancelled run destroys its iframe, which ends the worker and anything it started. A spare sandbox boots in the background, so every run starts with a fresh interpreter.
- **Results.** The worker returns raw results only: exceptions and tracebacks, `repr` and `json.dumps` of each return value, and stdout/stderr bounded to 64 KiB each with byte counts. Expected outputs never enter the sandbox. The app validates and bounds every message and renders all of it as text.
- **Conversion failures.** Turning a return value into `repr` and JSON runs user code too. A failing `__repr__`, an unprintable exception, a value nested more than 500 levels deep or cyclic, or one holding more than 1,000,000 nested items, which is too many to inspect, becomes a per-case `conversionError`, and earlier cases are kept. A value that cannot be inspected completely is refused, never assumed shallow. The depth limit exists because CPython's C-level `repr`, `json.dumps` and deallocation of very deep containers exhaust the wasm stack before Python's own recursion guard fires. For the same reason, returned values stay referenced until the sandbox is destroyed.
- **Failing closed.** If the runtime cannot load (hash mismatch, missing file, blocked worker, boot timeout), Run stays unavailable and the error is shown as a runtime failure, never as a user error.

`npm run test:browser` checks this in a real Chromium. The isolation check serves the runtime only with a synthetic HttpOnly sign-in cookie. It verifies that a signed-in page boots and runs, and that a missing or expired sign-in, a tampered file or a foreign asset base all fail closed, never following the sign-in redirect or sending the cookie elsewhere. Run `npm run build:cloudflare` first; the workspace half starts a local `wrangler dev` preview and never deploys.
- `tools/browser/sandbox-check.mjs` also runs JavaScript, TypeScript, SQL, HTML, PHP, Ruby, Go, C, C++, C# and Java through the same sandbox (the compiled languages in pages of their own, for memory): results, errors located in the solution file, timeouts, and attempts to reach the network (fetch, dynamic import, WebSocket, XHR, importScripts), use eval or IndexedDB, or read the parent page, all of which must be blocked. From Python it tries:
  - `fetch` to the app origin, another origin and a private address; XHR, WebSocket and EventSource.
  - `importScripts`, `eval`, and a fetch from a nested worker.
  - IndexedDB, caches, cookies, `document` and `parent`.
  - It also probes the frame document directly.
  - Two local servers must receive no request, while a positive-control normal worker does reach them.
  - It also covers timeout, cancel, clean reruns, output flooding and tampered assets.

Limits:
- **Memory and CPU.** There is no hard per-run memory quota in browsers; only wasm's own memory ceiling applies, and the timeout or cancel destroys everything. CPU is bounded by the 5 s timeout.
- **Startup.** The first run downloads about 13 MB; every run boots a fresh interpreter, about 2 s in headless Chromium.
- **Browsers.** Firefox and Safari/WebKit were not verified here: this host lacks their system libraries.
- **Engine stack.** If user code itself builds and frees a container nested about 3,000 or more levels deep, the wasm stack is exhausted. The run is then reported as a runner error and its cases are lost. Python-level recursion raises a normal `RecursionError`.
- **Forged results.** Python can forge result messages to its own frame, because tests run in the same interpreter. Feedback is practice only, not anti-cheat.
- **Tab focus.** Tab indents inside the editor; Escape then Tab, or Ctrl-M (Shift-Alt-M on macOS), moves focus out.

## Editor

CodeMirror 6 with an explicit extension list (`apps/web/app/practice/editor.ts`), every feature named in `editorFeatures` and recorded with each session:

- Highlighting and indentation for the challenge's language, Tab indenting, undo/redo history, bracket-match highlighting, line numbers, and Mod-Enter to run public examples (`mod-enter-runs-examples` in `editorFeatures`).
- Type hints for TypeScript and JavaScript, as an editor had them before AI: errors as squiggles shortly after typing stops, and the type of whatever is under the pointer. They come from the TypeScript language service (5.9, ES2023 library, strict; JavaScript gets syntax errors and inferred types, not type errors), in a worker of its own that only parses and checks the code (`type-checker.ts`). Its files are pinned like the runners'. `type-diagnostics`, `hover-types`, `keyboard-type-info` and `keyboard-diagnostics` join the recorded features when they are on. F1 opens and announces the type at the cursor; Escape closes it. F8 and Shift-F8 move through diagnostics and announce them; Ctrl-Shift-M (⌘⇧M on macOS) opens the diagnostics panel. These commands also work with Vim keys.
- Vim keybindings (`@replit/codemirror-vim`) when the profile chose Vim; the pane title shows the mode.
- A steady block cursor, as in a terminal. Syntax colours come from CSS variables (`--syn-*` in `practice.css`); the site is dark only.
- No autocompletion, auto-closing brackets, linting or AI assistance. Autocomplete is undecided: ask first (root `AGENTS.md`).

The editor owns its document, so typing does not re-render React, and work survives runs, errors, timeouts and cancels. The language's grammar and Vim are loaded on demand (`loadEditorModes`), so a challenge downloads only its own language's mode. Tab indents inside the editor; Escape then Tab moves focus out.

## Saving and restoring

Everything typed is recorded on the device as it happens ([telemetry](telemetry.md)), and that record is how code comes back.

- **Restore.** On opening, `packages/capture/restore.ts` rebuilds the attempt's latest saved code exactly, from this participant's practice records for this challenge and attempt only. Each page load's stream is replayed on its own, from a complete copy (the opening code or a snapshot), applying saved change sets in strict order and checking each revision and length. Replay stops at a missing position, a disclosed gap, or a truncated or invalid change, and restores the last exact document; the page says which revision was recovered. A new attempt opens on the starting code. When the challenge changed since the attempt last opened, the page says so.
- **Save state.** The code pane says **Saved** only when nothing is waiting to be written and the current code can be rebuilt exactly: a complete copy is stored and nothing at or after it is lost, conflicting or without a change set. Otherwise it says **Saving…**, **Save failing, retrying** or **Not fully saved** (a capture gap, an artifact conflict, or a large edit whose copy is truncated) until a later complete copy is stored; every run saves one. Edits still waiting when a page closes abruptly are not recoverable: recording never blocks typing.
- **View.** The cursor, selection and scroll, and whether the output is open, are kept per attempt under `muscle-memory.practice-view` (twenty attempts at most), never recorded.

## Checking it

- `node tools/browser/sandbox-check.mjs chromium` after touching the runner or a worker.
- `npm run check:publish` after changing a challenge's code or cases.
- `LOOP_ORIGIN=http://localhost:3000 node --import tsx tools/browser/practice-check.ts` against a running app: a start from the list, failing and passing submissions, completion, the questions, resuming, starring, practising again and the next challenge, with what each records. `tools/browser/integration-share-check.ts` covers the result card and a shared link.

## Completion feedback (ENG-375 owner correction)

Output is always visible after a check, without a success banner or output disclosure. Safe failures/rule violations remain actionable. Next stays beside Submit; Share opens the existing share dialog directly with code sharing unticked. There is no practice-again action or extra report/navigation panel in the result body.

Reflections have an explicit UI-only cooldown: one offer every five completed solves, starting at the fifth. The existing questions rotate across eligible solves. Choice and answer/skip dismissal stay on the latest attempt in existing local progress; reset/deletion clears them. Reload, repeated submit and rerender never select another question. Skip records no observation or inferred answer. This adds no questions or collection fields.

The optional FYI uses a median of at least three distinct models' successful, matched declared-default solutions, not nondefault/best-run substitutions. It counts Unicode code points including whitespace in the exact submitted file. Difference = (user length − median model length) / median model length × 100. Differences below 10%, missing/truncated/zero lengths, sparse or partial receipt coverage and incompatible contexts produce no FYI. The line labels shorter/longer code, never quality or speed. There are no per-model cards, methodology/availability prose, refresh controls or detail accordions here; analysis stays on the separate report. Stealth hides the FYI while preserving all grading/output.
