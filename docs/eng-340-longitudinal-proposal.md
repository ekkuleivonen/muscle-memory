# ENG-340: minimal longitudinal history proposal

**Option A direction approved by Ekku via dot on 27 October 2026. The exact verification binding and existing-token use are now approved through dot; prepared in source, not deployed from this branch.** See [the implemented boundary and approval request](eng-340-private-history.md), which supersede the proposed budgets, route placement and release status below. Option B remains unapproved and disabled.

Historical proposal: The comprehensive dashboard scope stays intact. The existing latest-attempt view is an immediate evidence source, not the final longitudinal architecture. No route, credential, disclosure, consent version, collection event or production retention setting is changed by this proposal.

## Recommended decision: reuse uploaded records, derive privately on demand

Choose **A: a device-secret-authorized private history reader over existing Cloudflare records**, without a new persistent summary store. It can recover earlier attempts that browser compaction already removed, where those uploads actually exist. Additional local retention cannot do that. Keep the implemented local-retention flag off.

The current server already retains account activity for the account lifetime, with deletion within 30 days, while browser compaction keeps each challenge’s latest attempt. This proposal does **not** extend server raw-data retention. Existing records and purposes do not themselves authorize a new participant-facing API: the reader still needs explicit owner approval, security review, and a disclosure review before release. In particular the current Privacy Notice says records are currently looked at only by the operator and uploads do not provide recovery/sync. Clarify private statistics access without implying code recovery or device sync; any notice edit requires the repository’s legal-version process. The implementation now includes a draft disclosure revision and legal-version bump for eventual release; neither is deployed.

## Minimal summary allowlist for either path

Keep one versioned record per participant / challenge / immutable revision / attempt, with explicit coverage and missingness. Retain this information only; no new activity collection:

- Interpretation and capture versions; challenge/test revision; recorded language/runtime fingerprint and editor/tool condition. If any condition is absent, label it unknown and exclude it from matched inference. Current catalog tags/difficulty are labelled current metadata; do not invent historical metadata.
- Attempt start/last/completion timestamps, observed completion, repeat/first/unknown status, source/session count and ordered coverage bounds. Missing positions, conflicting IDs, truncation, unsupported captures and uncertain tail/order remain explicit. A missing source cannot be assumed to contain zero activity.
- Unique example/submission run counts, decided first-submit outcome including static rules, passing-check checkpoints, user/test versus runner/loading/cancel/timeout counts, first edit/run latency, between-run time/edits and runner wait, with eligible-event denominators.
- Inserted/deleted volume and small/larger-edit buckets, undo/paste counts, snapshot/checkpoint counts; no edit text. Code retention/rewrites and recurring failure signatures stay unavailable until their deterministic definitions are validated.
- Editor key burst/interval/pause summaries, correction/navigation counts, interaction-active estimate with threshold/version, session span, focus/visibility and return counts; no raw key values or per-key timing vector. Do not infer attention, mistakes or distraction.
- Tooltip/diagnostic exposure counts and only the already-recorded optional retrospective attempt answers, labelled successful-completer-only. No claim that unobserved external assistance was absent. Do not copy the twelve-question profile or sensitive slices into every summary.
- Failed-check → improvement/completion counts and eligible recovery time, edit and distinct-check iteration counts. Bounded safe timeline: at most 200 typed outcome/checkpoint labels per attempt, with explicit truncation/coverage; no arbitrary exception strings, code, outputs, hidden tests or model/reference solutions.

Longitudinal presentation uses these per-attempt observations, not averages of averages: e.g. medians over eligible attempts, with numerator/denominator and retained/uploaded coverage. Same-revision repeated-task history is distinct from fresh-task coverage. Match recorded language/runtime/tool conditions and assistance context where available. Missing assistance context is not equivalence. No global “skill increased” score from different tasks, an easier mix, or successful completers alone. Fresh-task growth still requires a defensible matching method; it remains explicitly unavailable until validated, rather than pretending repeated-task speed proves transfer.

## A: concrete implementation boundary

1. Add a **POST-only same-origin private history route under the existing ingest Worker**. Reuse/refactor its existing device-secret ownership verifier for access/deletion; verify the SHA-256 secret against the current `CONTROL/participants/<id>` proof and check `deleted/<id>`. An ID, referral code, upload proof/hash or Terms cookie alone never authorizes history. Do not call the existing access-request endpoint as an authentication workaround: it writes a human access-request note and returns a reference, not a read capability.
2. No generic SQL, arbitrary subject ID, profile slice, raw-row projection or public history URL. The verified participant is the fixed query subject. Reuse existing R2 SQL/current-snapshot infrastructure and the tested interpretation registry. Any credential provisioning/rebinding is a separate approved operator step: the ingest Worker currently has CONTROL/Pipelines bindings, **not** the admin SQL token. Do not assume the existing token is already authorized or available in this route; do not mint credentials or broaden token privileges in ENG-340. If existing read authority cannot be safely reused as configured, report the exact binding change for approval.
3. Discover eligible attempt IDs in bounded pages, then derive one whole selected attempt/revision at a time with source order intact. Do not split an attempt by an arbitrary date window and call the fragment complete. Server-internal bounded reads may process that participant’s existing observation payloads for the shared deterministic interpreter; exclude artifacts and other participants. Return **only validated summaries**, never raw event payloads/code/keys. Exceeding a safe read budget yields an explicit incomplete/budget-limited attempt, not invented values. Fixed validation/escaping; no user-controlled SQL, paths or table names.
4. Initial proposed response/query budgets: at most **50 summaries / 256 KiB per response**, at most **10,000 observations / 4 MiB of internal input per attempt**, **15 seconds per query**, and a proposed rate of **one new history query per participant per minute** using a separately configured CF rate-limit binding (approximate across locations; coalesce identical in-flight requests). A hard global spend ceiling would need separately approved metering; do not promise the existing 120/minute upload limiter enforces this history budget. These are adjustable safety/cost limits, not history eligibility thresholds. Oversize attempts remain unavailable until a bounded streaming/checkpoint strategy is validated. Explicitly paginate older history, so a response limit is never represented as the account’s complete history. Treat the bounded pagination cursor as untrusted input: independently verify the subject’s secret, validate every position/query bound, and check the current snapshot on every page. Reject/restart a stale snapshot cursor rather than querying arbitrary historical snapshots. A cursor conveys no authorization and needs no new signing credential. No browser ID in public links.
5. `Cache-Control: no-store`; no CDN/HTTP/Cache API cache, no raw-response or credential logging. Optional **60-second maximum**, bounded private isolate-memory cache of code-free summaries; check current proof/tombstone before every serve and again after query/derivation, including cache hits. Invalidation on tombstone takes precedence over TTL; logout/reset clears the tab’s response and cancels/discards in-flight results. Cache keys include verified participant, interpretation version and query/conditions. Bounded eviction and concurrency prevent unbounded isolate memory/cost. No persistent derived-store erasure integration is necessary in this minimal version.
6. The dashboard’s **Load uploaded history** action explicitly selects account-upload history. It is a data view action, not new collection consent. Explain that reset clears this browser, not uploaded records. Default/reset view remains device-local; after reset do not auto-read or merge server history back into device progress. A person may explicitly request uploaded history again. Logout/delete revoke the current view; a late response cannot restore it. This avoids silently undoing reset or implying sync/recovery.
7. Reconcile current local pending observations with uploaded observations by `record_id` **before** deriving a merged attempt. Never sum overlapping local/server summaries. Prefer server summaries for fully uploaded attempts; show a local-only/incomplete status where the server lacks observations, until a server-authorized whole-attempt reconciliation exists. Include ingestion/query watermark and per-attempt coverage; the pipeline can lag by minutes, so the local completion remains immediate and its verdict is never replaced by stale aggregate state.
8. Tests before enabling: wrong/missing secret, ID-only/proof-only requests, deleted proof and tombstone races, isolation across participants, cache subject/version separation and expiry, reset/logout during query, no raw fields/logging, query bounds and pagination, late/duplicate/conflicting uploads, sequence across resumes, mixed revisions/runtime/tool conditions, stealth including historical exclusion, minors/small cohorts still suppressed. Test with synthetic data only. Integrate final merged ENG-371 loaders/private hydration/CI before release; ENG-373 workbench remains separately owned.

No new warehouse, service, paid model runs, public aggregate endpoint, cross-device account mechanism or collection schema is needed.

## B: exact local alternative if chosen

Approve a disclosure/legal-version change before enabling `PROFILE_HISTORY_ENABLED`. Implement the proposed 365-day / 2,000-summary / 8-MiB bounds and coverage markers **before** flipping the flag; the current tested path has atomic storage/clear semantics but does not yet implement those retention bounds. Expire before reads, compaction and backup export/import; do not extend retention merely because the dashboard was opened. A closed browser cannot run a scheduled IndexedDB purge, so bytes may remain on disk until the next visit even after the 365-day logical expiry. Do not promise wall-clock physical deletion from an offline browser; if that is required, reject option B. Repeated activity may update an unfinished attempt’s last-observed timestamp. Replace an attempt summary deterministically; never double count it. On interpretation changes, invalidate incompatible summaries and say that older raw evidence is absent; do not silently reinterpret old numbers. Backup/import must enforce expiry and size/count bounds too, and display the coverage restored.

This option can improve future offline history, but it is not a substitute for the server path when the promised dashboard needs earlier uploaded history. Do not describe “play more” as a remedy for previously compacted evidence.
