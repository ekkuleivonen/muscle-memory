# The IDE

`/work/<KEY>` (for example `/work/FN-1`, always on the issue's live revision) opens an issue in a VS Code-style IDE: a title bar with the issue's status and **Run tests**, an activity bar switching between the ticket and the file explorer, editor tabs, a bottom panel with **Tests** and **Output**, and a status bar with the branch, save state, Vim mode and runtime. An issue's **Start work** button links here and moves the issue to In progress.

**Run tests** (⌘⏎) runs the cases in the repo's test file against your code and changes nothing else; run as often as you like. **Open pull request** (⌘⇧⏎) is the deliberate step: CI checks that exact code revision with a run of every case, including the ones the test file leaves out. Its results show every case like a CI log does: input, expected value and what came back. The pull request then stays **Open**, whatever its checks say. While it is open the button reads **Push to #n**: more work goes to the same pull request and CI runs again, so there is only ever one open pull request per issue. To start over, close it without merging on its page (**Close pull request**); the next push opens a new one. A pull request left open after another of the issue's was merged shows a nudge to close it. Once its checks pass and no blocking comment is open, **Review and merge #n** becomes the main action, in the header and in the Pull requests tab, which also shows the review comments on it. You review it on its page at `/pulls/<KEY>/<n>` (the timeline since the previous pull request, including every push, every check with what came back, and the diff from the starter code, all derived from the observations below) and merge it yourself; merging is blocked until every check passes and every blocking review comment is resolved, and it moves the issue to Done. Teammates review pushes and comment on the ticket by fixed rules ([issue model](issue-model.md#teammate-comments)): the IDE checks after every run and push and every 30 seconds, says in the panel what arrived, and marks the Ticket view when its thread has something new. The Pull requests tab lists them across sessions. Until a runner server exists CI runs in the browser too, so the cases only CI runs ship with the revision; they are left out of the test file, not secret. What is never shown is the machinery behind teammates: comment triggers and their examples, and the reference solution.

Each issue opens as a small repo: the files of its live revision. `tools/build-content.ts` generates them at authoring time with `apps/web/lib/repo.ts`, so a seed issue needs only an entry point and starter, and the IDE shows exactly what was published ([issue model](issue-model.md)). Each file has a role: `edit` files are the ones you change (every one is editable and recorded), `read` files are source the program uses but you cannot change, `tests` is a read-only test file holding the acceptance criteria in that language's usual style (pytest, Vitest, a Go table test, PHPUnit, Rust integration tests, SQL fixtures, expected HTML), and `docs` are the README and, for SQL, the schema. The revision's `entry` names the source file that defines the entry point. Only runners that load several files (`multiFile` in `engines.ts`: JavaScript, TypeScript and Python today) accept more than one source file. JavaScript and TypeScript resolve imports between them; Python gets every file under `/repo` with the repo root and the entry file's folder on its import path, so `from shop.money import cents` and `import money` both work, and an edited file is imported afresh on every run. JavaScript, TypeScript and Python issues may place their entry file (`entry`), for example in a package. Every demo issue has a starter. All twelve languages offered in setup run in the browser: Python, JavaScript, TypeScript, SQL, HTML, PHP, Ruby, Go, C, C++, C# and Java. An issue in another language (none in the catalog today) opens for editing with Run unavailable. A case's input is the function's only argument, unless the issue names its `parameters`, in which case the input lists the arguments in that order. A SQL issue also carries a `schema` (CREATE TABLE statements, shown read-only as `db/schema.sql`); each case's input is rows per table, and its output is the rows the last statement returns. A case passes when the returned value equals the expected output as canonical JSON.

## Runtime isolation

Submitted code never runs in the app's JavaScript context, in Node or on a server.

- **Sandbox.** Each run gets a new `sandbox="allow-scripts"` srcdoc iframe. That gives an opaque origin with no access to the app's DOM, cookies, localStorage or IndexedDB. Inside it, a classic dedicated worker runs the issue's language. Every language uses this same boundary and message protocol; an engine (`packages/runner/engines.ts`) only adds its worker source (`packages/runner/workers/`) and pinned files:
  - **Python**: Pyodide, as below.
  - **JavaScript and TypeScript**: the browser's own engine. Sucrase strips TypeScript types, keeping line numbers, and every source file becomes an ES module at a blob URL, its relative imports (`./discounts`, `../money.js`) rewritten to its siblings' URLs; package imports are not available. A missing or circular import is a compile error naming the files, and a stack trace points at the file and line it came from. Nothing is type-checked when running. Each case gets a fresh copy of its input; a returned promise is awaited; values JSON cannot hold (NaN, BigInt, undefined) are refused rather than guessed.
  - **SQL**: PGlite, which is Postgres 18 compiled to WebAssembly. Each case runs in its own transaction, rolled back afterwards: the schema is created, the case's rows inserted, then the solution's statements run. Errors read like psql's, with the line and a caret.
  - **HTML**: checked the way frontend tests check a page. The markup is parsed into a DOM with linkedom (no scripts run, nothing loads) and each case is `[selector, read]`: the number of matches (`count`), their `text`, each form control's accessible `label` (aria-labelledby, aria-label, then its label), or an attribute. The repo shows these checks as a jsdom test.
  - **PHP**: php-wasm (PHP 8.4, used under its Apache-2.0 licence option). The solution is written into PHP's in-memory file system at its repo path and required, so errors name the right file and line; echo and warnings are its output. Its sockets are emulated over WebSocket, which the sandbox refuses, so none ever connects.
  - **Ruby**: ruby.wasm (CRuby 3.4 with its standard library). Inputs go in as Ruby literals and results come back through a small JSON encoder; `puts` is its output.
  - **Go**: Yaegi, the Go interpreter, with Go 1.25's standard library, built to WebAssembly from `tools/runtimes/go` (our own harness, not a prebuilt binary). The harness evaluates the solution's package and calls the entry point per case, decoding each JSON input into the function's real parameter types with reflection. A two-value return follows Go's idioms: a false `ok` or a non-nil `error` is reported as `null`. Runs happen on a goroutine, so code that blocks (channels, `time.Sleep`, `net/http`) works; `net/http` goes through fetch, which the sandbox refuses. Panics stay with their case, with the line Yaegi reports.
  - **C and C++**: Clang/LLD 22 compiled to WebAssembly (YoWASP), targeting WASI with wasi-libc and libc++. C has no reflection, so a C or C++ issue carries an `adapter`: a few lines that turn a case's JSON arguments into the function's types and the result back, using a small JSON library (`mm_json.h`) the runner compiles in. The repo shows the adapter and the cases as the test file. The program (solution, adapter, library and a `main` that reads the case from stdin) is compiled once per run, at `-O1` for C and `-O0` for C++, then each case runs as a fresh instance with only WASI imports, so a crash stays with its case. Because the program never runs in the worker's JavaScript, this sandbox is kept between clean runs: loading LLVM takes seconds, a rerun about half a second. Runs may take up to 30 seconds, compile included. On some hosts the browser's renderer dies on any WebAssembly memory trap (out-of-bounds access, C stack overflow) instead of throwing a catchable error; the browser check probes for that and reports the crash case as skipped there.
  - **C#**: .NET 9 compiled to WebAssembly with Roslyn 4.12 (C# 13), built from `tools/runtimes/csharp` in a digest-pinned .NET SDK image. Roslyn compiles the solution in memory against a curated set of the framework's reference assemblies (System.Runtime, collections, LINQ, regular expressions, numerics, System.Text.Json and a few more; no networking or file system), with `System`, `System.Collections.Generic` and `System.Linq` imported. The entry point is the public static method of that name; each JSON input is decoded into its parameter's type with System.Text.Json, and the result is encoded with camelCase names. Exceptions name the methods they went through, but not lines: writing the debug information that would map them needs a second thread. The runner's `Main` is called once per run with the request in .NET's in-memory file system, rather than through `[JSExport]`, whose generated wrappers get random names and would make builds differ.
  - **Java**: teavm-javac, which is OpenJDK 25's javac and the TeaVM compiler, both compiled to WebAssembly (WasmGC, so it needs a current Chrome, Edge or Firefox), built from a pinned commit in a digest-pinned JDK image. javac compiles the solution, the issue's adapter and a small JSON library (`Json`); TeaVM turns the classes into a WebAssembly program, and each case runs as a fresh instance of it with the case's arguments as `main`'s only argument. As with C and C++, a Java issue carries an `adapter`, because TeaVM keeps almost no reflection. TeaVM's class library covers most of `java.lang` and `java.util` (collections, regular expressions, `String.format`), not files or networking. Its own JavaScript interop (`org.teavm.jso`, `@JSBody`) is refused as a compile error. Exceptions show their type and message; without debug information TeaVM has no useful stack frames. A run takes one to three seconds, javac and TeaVM included.
  - **One exception to the sandbox's policy**: TeaVM's loader builds its JavaScript glue from source text, so the Java engine's frame allows `eval` (`allowEval` in `engines.ts`). It gives code nothing new: the frame is still an opaque origin with every connection, storage and the parent denied, and the JavaScript engine already runs arbitrary user code in the same kind of frame. Every other engine's frame refuses `eval`.
- **No network.** The frame's CSP is `default-src 'none'; connect-src 'none'; script-src '<boot-hash>' blob: 'wasm-unsafe-eval'; worker-src blob:`, plus `'none'` for every other fetch directive. Blob workers inherit it. There is no `unsafe-eval`.
- **Runtime files, sent once.** Each sandbox gets its own copy of the runtime's bytes, transferred rather than copied into the frame and on to its worker (runtimes run to 100 MB); the page keeps none and reloads from the HTTP cache, re-checking the hashes.
- **Runtime files.** Pyodide `314.0.7` (Python 3.14.2, about 13 MB), Sucrase `3.35.1` (one 47 KB bundle, gzipped), PGlite `0.5.11` (Postgres 18.6, about 5.5 MB gzipped), linkedom `0.18.14` (110 KB gzipped), php-wasm `0.2.0` (PHP 8.4.1, about 3.5 MB gzipped) ruby.wasm `2.10.1` (Ruby 3.4.1, about 9 MB gzipped) Yaegi `0.16.1` (Go 1.25.3, about 8 MB gzipped) YoWASP Clang `22.0.0-git20542-10` (about 27 MB gzipped), the C# runner (Roslyn `4.12.0` on .NET 9, about 8 MB gzipped) and teavm-javac `208d4c9` (about 4.5 MB gzipped) are pinned in `package-lock.json` and `packages/runner/runtime-manifest.json`. The `predev`/`prebuild` step `tools/build-runtimes.mjs` copies the binaries from `node_modules`, bundles the JavaScript pieces into single files with esbuild, writes them into the app's static assets and verifies every SHA-256 hash; after upgrading a package, `node tools/build-runtimes.mjs --update` rewrites the pins. The Go, C# and Java runners are built from source in images pinned by digest (Docker is required for the build); identical inputs give identical bytes, and builds are cached in `node_modules/.cache` by their inputs. Files over Cloudflare's 25 MiB static-file limit ship gzipped (`.gz`); the page checks the compressed bytes' hash, then unpacks them before handing them to the sandbox. The sizes are pinned too, so the IDE's opening screen can show download progress. A page loads only the engine its issue needs. Nothing loads from a CDN.
- **Loading inside the sandbox.** Only the trusted app page fetches the files. It uses its own origin only (`mode: "same-origin"`; an asset base on another origin is refused) and the site's existing sign-in, such as the Cloudflare Access cookie on the owner preview (`credentials: "same-origin"`). Subresource Integrity checks every file. Any redirect, for example to a sign-in page after the session expires, fails closed instead of being followed. The page then posts the bytes into the frame; the sandbox never sees credentials and makes no requests. The worker answers Pyodide's file reads from memory. Only the standard library is available: the package lock is empty, so other imports fail without any request.
- **Timeout and cancel.** A finished, timed-out (5 s) or cancelled run destroys its iframe, which ends the worker and anything it started. A spare sandbox boots in the background, so every run starts with a fresh interpreter.
- **Results.** The worker returns raw results only: exceptions and tracebacks, `repr` and `json.dumps` of each return value, and stdout/stderr bounded to 64 KiB each with byte counts. Expected outputs never enter the sandbox. The app validates and bounds every message and renders all of it as text.
- **Conversion failures.** Turning a return value into `repr` and JSON runs user code too. A failing `__repr__`, an unprintable exception, a value nested more than 500 levels deep or cyclic, or one holding more than 1,000,000 nested items, which is too many to inspect, becomes a per-case `conversionError`, and earlier cases are kept. A value that cannot be inspected completely is refused, never assumed shallow. The depth limit exists because CPython's C-level `repr`, `json.dumps` and deallocation of very deep containers exhaust the wasm stack before Python's own recursion guard fires. For the same reason, returned values stay referenced until the sandbox is destroyed.
- **Failing closed.** If the runtime cannot load (hash mismatch, missing file, blocked worker, boot timeout), Run stays unavailable and the error is shown as a runtime failure, never as a user error.

`npm run test:browser` checks this in a real Chromium. The isolation check serves the runtime only with a synthetic HttpOnly sign-in cookie. It verifies that a signed-in page boots and runs, and that a missing or expired sign-in, a tampered file or a foreign asset base all fail closed, never following the sign-in redirect or sending the cookie elsewhere. Run `npm run build:cloudflare` first; the workspace half starts a local `wrangler dev` preview and never deploys.
- `tools/browser/sandbox-check.mjs` also runs JavaScript, TypeScript, SQL, HTML, PHP, Ruby, Go, C, C++, C# and Java through the same sandbox (the compiled languages in pages of their own, for memory): results, errors located in the solution file, timeouts, and attempts to reach the network (fetch, dynamic import, WebSocket, XHR, importScripts), use eval or IndexedDB, or read the parent page, all of which must be blocked. From Python it tries:
  - `fetch` to the app origin, another origin and a private address; XHR, WebSocket and EventSource.
  - `importScripts`, `eval`, and a fetch from a nested worker.
  - IndexedDB, caches, cookies, `document` and `parent`.
  - It also probes the frame document directly.
  - Two local servers must receive no request, while a positive-control normal worker does reach them.
  - It also covers timeout, cancel, clean reruns, output flooding and tampered assets.
- `tools/browser/workspace-check.mjs` drives the built app through a Workers preview (it still targets the pre-IDE workspace page and needs updating for `/work/<KEY>`):
  - Edits, a normal run, syntax and runtime errors, truncation, timeout and cancel followed by reruns, an edit during a run (stale result), undo/redo/selection and typing responsiveness.
  - Device persistence: lifecycle order, correlation, no gaps, injected IndexedDB failures with retry, buffer overflow with a disclosed gap, recovery after reload and clear.
  - A tampered runtime.

Limits:
- **Memory and CPU.** There is no hard per-run memory quota in browsers; only wasm's own memory ceiling applies, and the timeout or cancel destroys everything. CPU is bounded by the 5 s timeout.
- **Startup.** The first run downloads about 13 MB; every run boots a fresh interpreter, about 2 s in headless Chromium.
- **Browsers.** Firefox and Safari/WebKit were not verified here: this host lacks their system libraries.
- **Engine stack.** If user code itself builds and frees a container nested about 3,000 or more levels deep, the wasm stack is exhausted. The run is then reported as a runner error and its cases are lost. Python-level recursion raises a normal `RecursionError`.
- **Forged results.** Python can forge result messages to its own frame, because tests run in the same interpreter. Feedback is practice only, not anti-cheat.
- **Tab focus.** Tab indents inside the editor; Escape then Tab, or Ctrl-M (Shift-Alt-M on macOS), moves focus out.

## Editor

CodeMirror 6 with an explicit extension list (`apps/web/app/workspace/editor.ts`):
- Highlighting and indentation for the issue's language (Python, JavaScript, TypeScript, SQL, HTML, PHP, Ruby, Go, C, C++, C#, Java, Rust; Markdown for the README), Tab indenting, undo/redo history, bracket-match highlighting, line numbers, and Mod-Enter to run.
- Type hints for TypeScript and JavaScript, as an editor had them before AI: errors as squiggles shortly after typing stops, and the type of whatever is under the pointer. They come from the TypeScript language service (5.9, ES2023 library, strict; JavaScript gets syntax errors and inferred types, not type errors), running in a worker of its own that only parses and checks the code. Its files are pinned like the runners'. There is no completion, and nothing AI-assisted; `type-diagnostics` and `hover-types` join the recorded editor features when they are on.
- Vim keybindings (`@replit/codemirror-vim`) when setup chose Vim; the status bar shows the mode.
- Syntax colours come from CSS variables, so the IDE follows light and dark mode.
- No autocompletion, auto-closing brackets, linting or AI assistance.

The editor owns its document, so typing does not re-render React, and work survives runs, errors, timeouts and cancels.

## Captured activity

Recording runs under the Terms and Privacy Notice accepted at `/consent` or `/play` ([legal.md](legal.md)), always on this device; each observation carries `terms-<version>` as its consent version. The aim is everything that happens in the IDE, as finely as it happens. Keys are heard only on the IDE's editors (editable and read-only), in the capture phase so keys an editor command consumes are heard too. The page is watched only for visibility, focus, size and pointer-or-keyboard input (to tell a person's navigation from the app's), and the clipboard is never read. Contracts live in `packages/domain/workspace.ts`.

- **Stream.** A page load is one source stream, `workspace-<uuid>`; a reload starts a new one. Each observation has a stable ID `<source>.<sequence>`, client `occurredAt`, `elapsedMs` (a monotonic clock from the start of the stream, in 0.1 ms steps, for exact intervals), an explicit absent server receipt, the capture version `workspace-capture-6.0.0`, a consent version, `researchConsent: false`, the issue's permanent id (`issue`) and the revision worked against (`issueRevision`, the SHA-256 of its content).
- **`opened`.** Records the person's profile as it stood then (experience, how often they code with AI, languages, goal, editor; null before any answers), where the IDE was opened from (the app page before it), the window size, the editor feature list (including the keymap, `vim-keybindings` or `standard-keybindings`), the runtime version (null for languages that cannot run yet) and declared capture gaps: pointer movement and hovering without a tooltip, layout resizing, activity in other tabs and apps, and writes cut short when the page closes.
- **`keys`.** Every key down and up and every IME composition in an editor, as `[elapsedMs, kind, key, modifiers, repeat]`, written per file about once a second (or every 200 keys). Keys carry their own times, so a batch is placed by time rather than by source position.
- **`selection`, `scroll`, `focus`.** Cursor and selection moves that change no text (bursts within 100 ms merge into one, with the number of moves and the last selection), the lines in view after scrolling (merged within 250 ms), and an editor gaining or losing focus. A merged burst is always written before whatever happens next.
- **`clipboard`.** A copy or cut in an editor: the ranges, or the cursors' whole lines when nothing was selected. Never the clipboard's contents; a paste is the edit it makes.
- **`assist`.** Help the editor showed: the type errors displayed (when the set changes) and each hover type opened.
- **`navigated`.** Files opened, shown and closed, the side bar (ticket or explorer) and the panel (tests, output, pull requests), each by `pointer`, `keyboard` or the `app` itself.
- **`page`, `runtime`, `closed`.** The page becoming visible or hidden, focused or not, or resized; the runtime loading, ready or failing; and the IDE being left (`left`) or the page being hidden as it unloads (`page-hidden-for-unload`). Leaving writes everything still buffered before capture stops.
- **`edit`.** One per document-changing transaction, naming its `file`, with the CodeMirror change set (up to 16 KiB), the user event (`input.type`, `input.paste`, `undo`, ...), the selection and the document length. Text pasted into the editor is part of the change; the clipboard itself is never read.
- **`snapshot`.** References a participant-owned `artifact.code-revision` holding every editable file by path (each bounded to 64 KiB with byte counts and truncation; its media type follows the file, `text/x-python`, `text/x-go`, `text/html`, ...). The revision number counts edits across all files. Snapshots are taken on open, every 25 edits, after an oversize edit and on every run.
- **`pull-request`.** One each time a pull request is opened or pushed to, once its checks finish: its number (1, 2, 3, … per person and issue, continuing across sessions), `push` (1 when opened, then 2, 3, …), the run that checked it, the code revision and artifact, the checks result (`checks-passed`, `checks-failed`, `checks-errored`, `cancelled`) and checks passed out of total. Merging is not recorded here but as the board move to Done ([board activity](board-activity.md)). Its run carries `purpose: "pull-request"`; Run tests carries `purpose: "local"`.
- **`run`.** Records `queued`, `running`, then `result`, `user-error`, `runner-error`, `timeout` or `cancelled`. Each carries the run ID, how it was started (`via`: a button or a shortcut), the exact code revision and its artifact, runtime and timeout. The terminal status holds the raw bounded outcome. A result for an earlier revision is shown as stale and never as feedback for the current code.
- **`comment`, `hint`, `thread-resolved`.** Teammate feedback as it is released: a comment (its id, place, severity, the wording shown and, for a review, the pull request and push), a hint (id and level), and a blocking review thread resolved by a push that no longer triggers it. Replies are recorded on the board ([board activity](board-activity.md)). What is due is worked out from these records and the revision's triggers, so nothing is released twice.
- **`capture-gap`.** Records an explicit lost position range (`buffer-full` or `write-conflict`).

Feedback is derived from the stored run outcome when shown. It is not stored, and a raw failure is kept whether or not it can be scored.

`packages/capture/recorder.ts` assigns positions immediately and writes ordered batches asynchronously, so storage never blocks typing.
- **Buffer.** It holds up to 1,000 records or 4 MiB. Failed writes keep the records and retry with backoff under the same IDs, so partial writes deduplicate. A changed payload under an existing ID is a conflict and is never overwritten.
- **Overflow.** When the buffer is full, the observation and the artifact it would add are dropped, but their position stays used. Once there is room, a `capture-gap` observation discloses the exact range. Typing stays responsive through all of this.
- **Storage.** Records go to the device-local IndexedDB database (version 4: a `workspace` store, the local identity and device secret, and the upload outbox), and from there to our servers ([telemetry](telemetry.md)).
- **Restore.** On reopening with device storage, `packages/capture/restore.ts` rebuilds the latest saved code exactly, using only this participant's workspace records for this issue, whichever revision they were written against. Board events with an issue context are not editor sessions.
  - Each source stream (page load) is replayed on its own and streams are never combined. Replay starts from a complete code artifact (the opening document or a snapshot) and applies saved CodeMirror change sets in strict source order, checking each revision and document length.
  - Replay stops at a missing position, a disclosed capture gap, a duplicate position, or a truncated, missing or invalid change or snapshot. The last exact document is restored, and the page says which revision was recovered and whether a newer saved code revision exists; missing activity alone does not claim that a newer edit was lost. A later complete snapshot is a new safe starting point.
  - The stream with the most recent saved activity is used. If it has nothing recoverable, an earlier session's code is used and labelled as such.
- **Save state.** The page shows whether code is kept in this tab only, still being saved, failing and retrying, or not fully restorable.
  - "All changes saved" needs two things: nothing is waiting to be written, and the current code can be rebuilt exactly. That means a complete copy (opening document or snapshot) is stored, and nothing at or after it is lost, conflicting or without a change set.
  - A large edit without a change set whose copy is truncated (code over 64 KiB), a capture gap, or an artifact conflict shows "cannot be fully restored after a refresh" until a later complete copy is stored; Run saves one. A conflicting payload is never overwritten. A snapshot that only references an artifact already found conflicting, such as a repeated Run with no edit, is not a complete copy.
  - The recorder tells the page as soon as the first edit makes the code dirty, and again when writes drain, fail or lose something. It does not notify on every keystroke.
  - Edits still waiting when a page closes abruptly are not recoverable; recording never blocks typing to wait for storage.
- **Clear.** Clearing first stops capture and waits for any write in flight, then clears the tab's memory or the device database. On the device this removes attempts, workspace records and the local identity together.

Not included: editor timelines beyond transactions, keystroke timing, participant uploads, exports of workspace records, server receipt, research collection or analytics. Copies made outside the browser need separate deletion, and browser storage can be evicted.

## Small screens and keyboard access

Below 860px, Ticket and Files open native modal drawers; Escape closes them and restores focus. Run and pull-request controls wrap, while the editor and result panel retain their own scrolling. File, result and pull-request tabs support arrows, Home and End with roving focus and labelled panels. The `?` button explains run shortcuts and Escape then Tab to leave the editor; shortcut labels use Ctrl on Windows/Linux and Command on macOS.
