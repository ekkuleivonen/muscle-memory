# Hourly comparison summaries — disabled draft

**Delivery path (current, 28 October 2026).** Human comparisons are built on demand, not by the scheduler below. `/api/cohort/<key>/<revision>` serves the private snapshot when it is at most an hour old and its generation is still current. On a miss it answers "unavailable" at once and, after the response (`waitUntil`), runs one bounded build of that one revision (`humanSummaryOnRequest`, `packages/statistics/scheduled-cohorts.ts`). A per-revision lease, claimed by an atomic R2 conditional write, allows one build per revision per clock hour and privacy generation across all isolates, at most 3 in an hour (an acknowledged privacy change anywhere invalidates every snapshot, so a rebuild for the new generation may run within the hour); a failed build is not retried for that generation within the hour. A build writes its snapshot only if its generation is still current, conditionally on the stored snapshot's ETag, so a slower older-generation build never replaces a newer one. One build is: 1 D1 read, 1 source get, 1 fixed member query (15 s, 1 MiB, 1,000 rows), 1 generation read, at most 2 × 5 member-check batches and 1 snapshot write, capped at 25 s. Upper bound: three Basin queries per viewed current revision per hour (one per hour without privacy changes), triggered by page requests (which reverses the earlier "no SQL on page loads" rule; activation needs that decision). The scheduled refresh, discovery query and rotation below are preserved draft work, not wired: no cron is configured.

Personal device answers render immediately. The existing web Worker precomputes only the metadata needed by tiny comparison sentences; page requests never scan global events. Models and human participants have separate snapshots and eligibility rules. No model execution, new event, service, credential, database or Mac/dev-01 dependency.

## Work limits and expected cost

One scheduled invocation has a combined ten-minute deadline. Model refresh uses at most45seconds: up to 100 of at most 200 current revisions per run (stalest first, see below),250 receipt GET attempts,32MiB declared receipt-object bytes,100 writes of128KiB maximum. It reuses existing offline results, never runs a model. Model snapshots expire after two hours, bind the current harness, and never fall back to raw receipts on a player request when enabled.

Both refreshes read a registry of at most **200** current revisions (141 at the planned launch); over that they stop whole rather than drop revisions silently. This bound sizes the one discovery query; it is not a query budget.

Human refresh first runs one fixed discovery query for all registered current non-synthetic revisions, returning each potential group (at least 20 distinct starters) with its distinct-starter count. Discovery does not prove eligibility; the count is an upper bound on a build's members, used only to plan work.

**Work per hourly run, binding limit first.** Cloudflare documents that "a single request has a maximum of 32 Worker invocations, and each call to a Service binding counts towards this limit". The wording reads as a total, not a nesting depth; local workerd (Miniflare) enforced neither 250 sibling calls nor a 40-deep chain, so it cannot confirm production behaviour, and how scheduled events are counted must be confirmed read-only before activation. The run is therefore planned in **14 CONTROL slots**: a slot is one `check()` batch of at most 100 IDs before and one after, and a build reserves `ceil(potential browsers / 100)` slots (at most 5: 500 browsers, which also keeps the member query inside its 1,000-row bound). With one generation read per run that is at most **29 service-binding calls**, a hard stop in code. Resulting per-run ceilings: ≤15 Basin queries (1 discovery + ≤14 member queries; all operations are in the table below), ≤14 × 2 × 100 × 3 = **8,400 CONTROL reads** (under the earlier 59,400 ceiling), two builds concurrent, the same 90-day windows and 10-minute deadline. A build that returns more members than it reserved fails closed before any check. Revisions over 500 potential browsers are *oversized* and never built; candidates that don't fit a run's slots are *deferred*.

One generation is read per run, before any member check, and tags every snapshot built in it; serving re-authorizes that generation on every read, so a privacy change acknowledged during the run makes them unservable without a second read per build.

**Trade-off.** At 14 slots a run, 141 small candidates are each rebuilt about every 10–11 hours, while snapshots expire after one hour: most human lines are missing at any moment. Any acknowledged privacy change by anyone advances the one generation and invalidates every snapshot until rebuilt. Options for the owner, none implemented: a longer snapshot lifetime (freshness only: privacy is enforced by the per-read generation check, not the lifetime); more frequent runs (a cron change, each run within these limits); or confirmation that scheduled events allow more binding calls, which would let the slot count rise within the 59,400-read ceiling.

**Ordering and coverage.** Each run plans its work in a fair order with no stored state beyond the snapshots (`fairOrder`). First come a few candidates from a fixed hourly rotation over the key-sorted list (4 human, 4 model), regardless of past success or failure. Then come the rest, stalest first: never built, then oldest, then by key, from one listing of the cache's own snapshot prefix (keys and upload times only), or by rotation if the listing fails. A frontier of revisions that keep failing or stalling therefore can't starve healthy ones: each revision is a rotation pick once every ceil(n / 4) runs (36 for 141) and is attempted first in that run. Each human build has its own time cap (15 s + 20 s per slot of the 10-minute budget), and caps sum to at most 490 s, so every planned build starts even if all of them stall. Each model read is capped at 5 s and the listing at 5 s, so the rotation picks always start within the 45 s model budget. Tests cover never-buildable and stalled frontiers for both caches.

Each run reports actual work. Human: `registered`, `discovered` (null unless discovery ran and was valid), `selected` (planned), `attempted` (started), `refreshed`, `failed` (started, no snapshot), `deferred`, `oversized`, `notRefreshed`, `slots`, `rpcCalls`, and `complete`, true only for a valid discovery whose every candidate was refreshed in this run. Model: `registered`, `planned`, `attempted`, `refreshed`, `failed`, `remaining` (never started), `notRefreshed`, `complete`.

A100-revision synthetic run proves the100-query and two-concurrent-build bounds. A stubborn mocked SQL transport stops at the remaining whole-run deadline.
