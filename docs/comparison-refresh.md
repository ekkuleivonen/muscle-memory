## Work limits and expected cost

One scheduled invocation has a combined ten-minute deadline. Model refresh uses at most45seconds: up to 100 of at most 200 current revisions per run (stalest first, see below),250 receipt GET attempts,32MiB declared receipt-object bytes,100 writes of128KiB maximum. It reuses existing offline results, never runs a model. Model snapshots expire after two hours, bind the current harness, and never fall back to raw receipts on a player request when enabled.

Both refreshes read a registry of at most **200** current revisions (141 at the planned launch); over that they stop whole rather than drop revisions silently. This bound sizes the one discovery query; it is not a query budget.

Human refresh first runs one fixed discovery query for all registered current non-synthetic revisions. Only potential groups with at least20 distinct starters get exact member queries. Discovery does not prove eligibility. Up to99 exact queries plus discovery (100 total), two builds concurrent, within the remaining whole-run deadline. Each exact query uses a server-selected interval bounded by publication and at most90days, a15-second transport deadline,1MiB response and1000-row limit; at most100 browser IDs undergo current CONTROL checks. Each metric separately needs20 eligible adult browser participants with exact revision/runtime/editor conditions and first/repeat separation. Unknown/minor/currently-excluded state is not counted.

**Ordering and coverage.** Each refresh lists its own private snapshot prefix once (keys and upload times only) and builds the stalest first: never built, then oldest, then by challenge. A revision left out by the 99-build cap, a read limit or the deadline is therefore first in the next run; with 141 human candidates every one is rebuilt at least every second run when runs complete, and fairly later when deadlines cut them short. If the listing fails, a stateless hourly rotation is used instead. Each run returns `registered`, `discovered`/`attempted`, `refreshed`, `notRefreshed` and `complete`; a run is never reported complete unless every candidate was refreshed. Because human snapshots expire after one hour, with more than 99 human candidates some FYIs are missing at any time, by design.

Human artifacts expire after one hour. Serving requires their generation to still be current on every read (a read of the fence, no write); an acknowledged opt-out/deletion invalidates old artifacts even within TTL. Missing, expired, mismatched, invalidated or interrupted data omits the comparison sentence. No stale fallback or request-triggered recomputation. More candidates than the work/deadline permits can temporarily lack a comparison; personal answers remain available.

## Evidence and remaining gates

Focused fixtures exercise cold/warm/expired snapshots, transient model read failure, harness changes, malformed inputs, generation invalidation and SQL-free serving. A100-revision synthetic run proves the100-query and two-concurrent-build bounds. A stubborn mocked SQL transport stops at the remaining whole-run deadline. Existing real local Workers/D1/R2 and CAS tests complement the SQLite/DataFusion query scenarios; they do not prove native Basin JSON behavior.

Native Basin verification passed through the authenticated admin SQL workbench on 27 October 2026. The synthetic CTE references default.events only through WHERE 1=0; it selects no player rows. Basin rejected the original table-free scalar probe, so the corrected scalar query uses a constant projection over one table row. This proves the native positive query path and JSON behavior, complementing the broader local negative-case suite; it is not proof of the owner's missing-history request.
