# Your report (ENG-374) and the observed developer profile (ENG-340)

`/stats` is a private report behind the existing Terms gate: a short story of six adaptive chapters, each one headline, one visual and, only where a player needs it to read the finding correctly, one short line of context.

**Players see insights, not data** (owner direction, 27 October 2026). The page shows no revision hashes, harness or protocol versions, receipt or cache timestamps, formulas, matching or debug statuses, and no methodology disclaimers, not even behind a disclosure. A finding the evidence can't support is left out, not explained. The ENG-340 measurement inventory below (definitions, eligibility, sample rules) is internal documentation and is no longer rendered for players. Consent, privacy choices and the legal notices are separate and unchanged; the report links to the Privacy Notice and settings.

## The report

**A portrait through simple questions** (owner direction, 27 October 2026). `/stats` answers a few questions about how you code, each from evidence already recorded; no new collection. A question the evidence can't answer is left out, never filled with zeroes or explained. There are no inventories (finished, open, revisited, waiting), no chapters and no comparison section. A comparison is at most one tiny FYI on the answer it belongs to. Players see no revision hashes, protocol labels, read times, formulas, matching or debug states, or methodology, even collapsed; the ENG-340 measurement inventory below is internal documentation. Consent, privacy choices and legal notices are unchanged; the page links to the Privacy Notice and settings. `apps/web/lib/report.ts` builds the questions, purely and deterministically (`report.test.ts`).

The one FYI today is on "iterate": the median submissions of models that solved the same challenges, each model try counted once however often you solved that challenge, using each model's declared default setting's first try (`defaultComparisons`, shared with practice) and only tries on the same runtime and diagnostics. Pending, unreadable or incomparable model results add nothing. Human comparisons stay off (`COHORTS_ENABLED = false`, [human cohorts](human-cohorts.md), ENG-376); when enabled they would also be a single FYI on the relevant answer.

**Caching, precisely.** Two short-lived caches exist, both from existing infrastructure:
- uploaded-history summaries are kept in page memory, keyed by participant, while the report is open and for at most five minutes after (a timer drops them);
- model receipt metadata is cached on the server for 60 seconds per Worker isolate (at most 32 revisions).

There is **no** scheduled or durable global precomputation, and **no** new retained personal-summary cache: nothing about a player is stored for the report beyond what practice already keeps. A prefilled, clock-refreshed global bundle would need new scheduling or configuration and isn't built.

A new player sees one line and a start. Someone who has started but has nothing answerable yet sees one line and a resume. Stealth shows only what stealth means and a link to privacy settings. The page uses the shared terminal geometry.

### Data, freshness and boundaries

On an ordinary visit the report reads this device's evidence first and renders it. In parallel it reads the owner's uploaded summaries (the past 366 days, first page of five attempts, through the existing secret-verified `/api/private-history`) and model receipts for up to three solved revisions (`/api/model-receipts`), for the iterate FYI. Each arrives independently; a slow or failed read shows a one-line status, never a blocked report. Uploaded summaries stay in page memory while the report is open and, keyed by participant, for at most five minutes after (a timer drops them), so moving around the site doesn't re-query. The report reads the first page automatically; there is no player-facing paging. A rate-limited or failed read shows only that earlier practice couldn't be added. Boundaries are counted per tab, so a nested one (deletion wraps reset) keeps every report blocked until the outermost finishes, including a report opened mid-boundary.

Device and uploaded attempts are deduplicated by attempt and revision (the trace with the later last observation wins, the device on a tie). Chapter 1 labels whether uploads contributed. Nothing read from uploads is written to progress, storage or backups.

Reset, deletion and import start a private boundary: the report, pending reads and the in-memory copy are cleared synchronously and reads are blocked until the boundary finishes. The open report then re-reads only this device and shows "uploads not re-read"; it never re-reads uploads in that same interaction, and nothing is ever written back to progress. A later deliberate visit (a new mount) reads still-retained uploads normally, because reset doesn't delete them (the reset page and the Privacy Notice say so). Account deletion clears the browser's identity, so no later visit can request history either ("no uploads linked"), and the server's tombstone refuses any request regardless. Logout, consent changes and stealth clear everything and read nothing. A boundary while `/stats` is closed still drops the in-memory copy (listeners are registered once per tab).

**Stealth** means no report: no device read, no history request, no receipt request. Server-side, stealth is a browser setting the server cannot read without another owner-scoped query, so the private-history route does not enforce it; this is not a privacy gap, since that route returns only the verified owner's own summaries, and the receipt route returns no personal data. Exclusion of stealth participants from any future human aggregate must be enforced where aggregates are computed, using the uploaded stealth answer (`site.profile`), not by hiding UI.

## Evidence and definitions

`packages/developer-profile/registry.ts` is the definition and threshold registry. `developer-profile-2` is an interpretation version, independent of capture. Every metric needs at least one eligible attempt/revision. There is no threshold to unlock a rank or percentile. Counts are per attempt; the overview of a metric is the median across eligible attempts, except first-submit success, which shows numerator/denominator. These medians describe the selected task mix; they do not establish growth. Repeats can be filtered separately; without an explicit repeat start or an earlier retained completion, first/repeat status remains unknown.

The pure reader deduplicates on stored `recordId` (the server's `record_id`), then orders each source by sequence. It uses the original per-key timestamps, never the batch delivery time. Wall clock orders separate sources approximately; it never subtracts independent monotonic clocks. Missing positions, explicit capture gaps, conflicting IDs, non-monotonic clocks, unsupported capture versions and missing starts withhold derived values for that attempt. Missing values are `null`, never fabricated zeroes. No retained trace can establish that an unseen closing tail was recorded.

## Local history and privacy

**Release gate:** `PROFILE_HISTORY_ENABLED = false`. The current Privacy Notice promises latest-attempt-only local storage; ENG-340 does not change consent or that promise. By default the dashboard uses the latest raw attempts retained on this device; explicit uploaded-history loading is separate. The tested summary path is implemented for a subsequent approved disclosure/version change, but the uploader does not enable it.

When enabled, before compaction removes an older uploaded attempt, the existing IndexedDB transaction saves its code-free interpretation in `settings[developer-profile-summaries]`. An attempt with any queued observation stays whole until it can be summarized atomically. The latest attempt's raw evidence remains available as before. If summary derivation/storage fails, the transaction aborts without deleting raw evidence. Summaries include the interpretation version, private attempt identity/revision, counts, conditions, optional retrospective answers and at most 200 timeline labels. They contain no code, raw keys, test outputs or reference solutions and are never uploaded.

The reader combines these summaries with current local records, with current records taking precedence. History compacted before this feature is not recoverable here. Changing interpretation versions invalidates old summaries; absent raw evidence is not silently reinterpreted. This disabled local alternative adds no public ID-based reader. The approved option A implementation below reuses existing CF queries and erasure, with the separately approved verification binding.

Existing backup export/import carries summaries in the store settings. Reset clears them with observations while keeping the device proof so uploaded data stays deletable. Account deletion clears the identity and summaries too. Reset change notifications occur after the clear, so open dashboards cannot refresh before deletion finishes. No server derived store or public response is added, so existing server erasure needs no new propagation target.

Stealth keeps own private stats available, hides all human/model comparison details and makes no comparison requests. Future aggregate release still must exclude stealth participants, including historical data, enforce approved minimum counts across combined slices, and keep 16–17-year-olds separate or excluded. None of that is bypassed by this dashboard.

No event, question, runtime tooling or model call is added. The draft Privacy Notice/version changes for eventual release; no live consent change is made. Local historical retention remains off under option A. Profile context uses existing editable/skippable settings, coordinated with ENG-333/356–367 by linking rather than creating a new prompt mechanism. No age nudge, demographics gate or promised percentile.

## Root-review corrections and model receipt boundary

Interpretation v2 adds genuine pre-test user-code error recovery. `errored` alone is not a classifier: it must join a terminal `user-error` with compile/runtime phase; runner/loading failures, cancellations, timeouts and unclassified errors remain separate. Reaching tests after such an error is an observed improvement, not completion. First-submit success treats that genuine user failure as unsuccessful and keeps infrastructure/unclassified outcomes unavailable.

Private snapshots now use a generation-checked external store. Reset/delete/import start a transient same-tab/BroadcastChannel invalidation before asynchronous storage work; privacy/account/progress storage events also invalidate. Event handlers flush the cleared view synchronously, pending generations cannot publish success/error/loading over the boundary, and clearing blocks rereads until it finishes. Failed post-boundary reads have no old snapshot to retain. Ordinary focus/manual refresh failures may retain a clearly labelled stale view. Logout/invalid consent prevent reads. Model requests have their own generation/abort boundary and cannot restore results after stealth/reset/logout. This adds no observation or persistent history.

`GET /api/model-receipts/<key>/<revision>` returns only allowlisted offline model metadata for a registered public revision behind the current Terms gate. It accepts no participant ID, code, profile or history. It uses existing catalog D1 and private CONTENT R2 bindings, querying fixed slot fields for the current harness and reading fixed `model-runs/stored/` then `outbox/` keys. The server validates model actor/session/revision/source coverage, ledger/start/end agreement, exact system/tool protocol and reasoning configuration, completion checks, runtime and feature allowlists before projection. No code, output, prompts, reasoning, arbitrary error/reason strings, artifacts, run IDs or participant IDs are returned or logged. No benchmark execution or credentials are added.

Reads cap at 25 slots and 8 MiB per receipt with a real 15-second database/stream deadline, with truncation/read-unavailable states instead of made-up outcomes. Server metadata cache is bounded to 32 revision keys for 60 seconds, coalesces duplicate revision reads, and allows at most two uncached reads per isolate; HTTP responses use no-store. Missing objects are not model failures. Existing R2 copies already used by the model event store are reused; no derived store or player-erasure target is added. Model results refresh separately from immediate local completion. Browser matching checks the recorded runtime and diagnostics condition, lists the different input/hover tools and unknown external assistance, and avoids claiming a controlled equal-assistance comparison. Provider-reported IDs are shown exactly; an alias is not called a pinned version. Models do not supply a human cohort, score, percentile or success probability.

The secret-authorized **player** history direction is approved and implemented with the owner-approved verification binding prepared in source, whose specific security-boundary approval has now been granted via dot. This model metadata route does not implement, bypass or substitute for that private access path. Unsupported human cohorts remain suppressed.

## Loading repair

Existing device progress appears before IndexedDB interpretation. The selective evidence reader excludes code artifacts, upload queue and unrelated settings. Local storage and identity waits have eight-second deadlines. Model reads have a twelve-second end-to-end deadline and at most two concurrent requests; transient capacity results get at most one retry after the batch. History remains independent, guarded against duplicate pagination requests and invalidated by existing privacy boundaries. No collection, capture, retention, permissions or human-cohort activation changes.

**History recovery.** A failed uploaded-history read keeps everything already shown and records a fixed reason code: `http-<status>`, `http-<status>:<server diagnostic stage>`, `timeout`, `network`, `identity` or `invalid-page`. The code goes on the status line's `data-history-reason` attribute and into one `console.info` line, never into the visible copy, and never includes the request, identity or response text. Rate limits, 5xx, timeouts, network errors and a slow identity read are retried automatically up to twice: identity after 10 s, everything else at the server's 61 s read interval. A body that is slow or cut off counts as a timeout or network failure; only a complete body that isn't a page object is `invalid-page`. Ownership refusals (401/403/410), other 4xx and malformed pages are not retried. After that, a "Try again" button and returning to the tab retry once more. One pacer per tab (`HistoryPacer`) holds the 61 s read interval and the retry budget across report remounts: a remount, click or focus inside the interval waits for it ("Adding your earlier practice…"), and only a successful page refills the budget. Reset, deletion, import, logout and stealth cancel pending retries and discard late replies as before.


Repair verification uses synthetic browser fixtures, not human research. At 1280/390 px the shared shell starts at 48/16 px; three receipt keys run with a peak concurrency of two. A selective read of 43 observation records takes about 5 ms in the local Chromium fixture and omits five 1 MiB artifacts plus the outbox. With the actual local compiled storage-open call made deliberately non-settling, existing progress renders in 91 ms and the eight-second deadline ends the pending read without hiding that progress. These are local fixture timings, not production latency promises; a separate pre-repair production shell sample was 1.17 s and did not reproduce the owner's full delay. The unbounded hidden measurement appendix was removed rather than retained behind a disclosure.
